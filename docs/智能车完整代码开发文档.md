## 0. 先定下不能写错的几件事

1. 参考车是四轮结构，左右各两个轮子；同侧前后轮由齿轮联动。应用层控制两侧电机，运行两套侧速度PI。
2. 图像中白线在右侧，应该使左侧两轮更快、右侧两轮更慢，使车头右转。
3. 编码器测的是所在轴转动；需要换算到轮端。轮胎滑移时，轮端圆周速度不等于真实对地速度。
4. 四轮转弯有横向擦地。差速公式是控制近似，初期用几何轮距，落地标定后使用等效轮距。
5. 十字路口必须直行；Y岔路两圈分别走两支；环岛须进入并绕完一周再离开。
6. 摄像头先看见出口，不代表后轮已过路口。状态解除需要考虑相机位置、前后轴位置与通过进度。
7. 普通循迹保持两侧向前；降低车速时一起约束转向，禁止因保留旧角速度而突然原地旋转。
8. 当前DRV8701板没有接回可用的电机电流和故障反馈。软件不能凭空实现电流闭环；占空比限幅不是硬电流限制。
9. 发车后不接受上位机或无线改参、速度指令、路线选择、启停命令。启动会话后使用冻结的参数快照。

开发目标分两层：先完成可观察、可停下的低速循迹程序，再加入十字、Y与环岛。不能把尚未适配现场的识别占位函数返回“成功”，然后允许正式发车。

## 1. 与模板仓库怎样衔接

### 1.1 本次源码核对结果

| 模板事实 | 编码时的处理 |
|---|---|
| `User/main.c` 只有时钟、debug初始化和空循环 | 保留已有基础初始化，再接入应用初始化和主循环 |
| `pwm_init(pin,freq,duty)`、`pwm_set_duty(pin,duty)`，`PWM_DUTY_MAX=10000` | 应用使用0～1占空比，底层统一换算到0～10000 |
| `gpio_init`、`gpio_set_level` 已有 | PH方向与EN输出只由电机适配层管理 |
| `encoder_get_count()` 返回 `int16`；正交模式下读取定时器CNT | 适配层恢复16位位模式，再做回绕差分，不把返回值直接当本周期增量 |
| `encoder_clear_count()` 会写CNT=0 | 连续采样期间不反复清零，避免读/清之间丢计数 |
| `encoder_quad_init()` 使用 `TIM_EncoderMode_TI2` | 有效轮端计数要实测，不默认PPR×4 |
| `pit_ms_init()`、`pit_enable()`、`pit_disable()` 已有 | 用真实的定时器枚举，资源分配后接入对应现有IRQ |
| `User/zf_isr.c` 已定义TIM、DVP、UART等IRQ | 在已有函数内接应用钩子，不能另加同名IRQ |
| `mt9v03x_init()` 返回0表示该初始化路径成功 | 初始化失败保持电机禁止运行，并显示错误 |
| 图像为 `uint8 mt9v03x_image[120][188]` | 单帧22560字节；处理逻辑按实际宏取宽高 |
| DVP初始化把BUF0、BUF1都设为 `mt9v03x_image` 地址 | 当前是同一图像存储区，不能当作两张独立帧 |
| DVP IRQ调用 `camera_dvp_handler()` 后清帧完成标志 | 保留原有回调链，每帧只加一次应用通知 |
| `Link.ld` 当前为288KB FLASH、32KB RAM，栈预留2048字节 | 先做内存预算，再决定实际内存分区和采集方案 |

源码还有两个值得注意的地方：摄像头头文件声明与实现中的部分handler命名不同，应用优先保留已有通用回调链，不能凭名字直接调用一个未定义的函数；`mt9v03x_init()` 内部给 `dvp_camera_init()` 的长度参数使用图像总字节数，不能仅凭参数名猜测并改成188，要按DVP硬件寄存器含义和现有工作方式验证。

### 1.2 文件改动范围

第一版将应用 `.c/.h` 平铺在 `User/`，不立即引入多层目录。现有工程已经包含User头文件搜索路径；根source entry会覆盖User源码，新增文件后检查构建输出是否生成相应对象文件。

| 文件/目录 | 计划 |
|---|---|
| `User/main.c` | 加应用初始化和主循环 |
| `User/zf_isr.c` | 在已分配的控制定时器IRQ、DVP IRQ中接钩子 |
| `User/*.c/.h` 新应用文件 | 实现本文规定的模块 |
| `zf_driver/`、`zf_device/` | 先复用；若图像暂停/恢复必须改变驱动，记录具体差异并单独验证 |
| `.cproject` | 检查新增源码、编译宏、链接配置；无需为每个User文件重复加source entry |
| `Ld/Link.ld`与实际芯片内存设置 | 内存分区确认后成对处理，不能只改链接长度 |

当前读取的 `SystemInit()` 没有展示一个可直接改成64KB的分区选项。不能假定“改system文件里的某个宏”就完成分区。实际芯片分区如何生效，应按WCH对应型号资料及烧录配置核对。

### 1.3 board_port.h 的硬件边界

下面接口为应用适配层，名字不是现有库API。`BoardIrqToken`保存调用前的中断屏蔽状态，底层表示由该芯片的中断机制确定，不在文档中伪造寄存器常量。

```c
uint32_t board_time_ms(void);
uint32_t board_time_us(void); /* 执行时间测量；回绕同样用无符号差值 */
BoardIrqToken board_irq_save(void);
void board_irq_restore(BoardIrqToken token);
void board_memory_barrier(void);
bool board_motor_init_zero(void);
void board_motor_write_en(SideId side, uint32_t duty_ticks);
void board_motor_write_ph(SideId side, bool electrical_level);
uint16_t board_encoder_raw16(SideId side);
bool board_camera_hold_after_frame_isr(void);
bool board_camera_restart_full_frame(void);
```

实现对应关系：EN由pwm_init/pwm_set_duty支持，PH由gpio_init/gpio_set_level支持；raw16在已确认的正交模式下用库读数恢复位模式。board_motor_write_en检查范围不超过PWM_DUTY_MAX，调用者仍需先通过运行权限和电机层检查。

hold返回true必须代表后续DMA不会继续写这张图，restart返回true必须代表从正确边界接收下一完整帧。接口无法履约就返回失败并禁止视觉驱动；不在适配层用关中断假装停止硬件。board_irq_save/restore及屏障必须针对本仓库WCH工具链实现并验证，不能照搬ARM汇编。

## 3. 统一单位、方向与命名

| 量 | 单位/方向 |
|---|---|
| 距离 | m；参数名含`_m` |
| 速度 | m/s；参数名含`_mps` |
| 角度/角速度 | rad、rad/s；左转为正 |
| 时间 | 调度/超时使用uint32毫秒；计算积分时转成秒 |
| PWM需求 | float，普通前进0～duty_limit；台架反向模式才允许负数 |
| 车辆前进 | 左右侧编码器修正后的增量均为正 |
| 图像横向误差 | 向右为正；对应负的转向角速度需求 |

side编号固定：LEFT=0、RIGHT=1。四个接触点编号固定：LF、LR、RF、RR。`side_speed`表示侧轮端圆周速度估计，不命名为“真实车速”。

编码器轴到轮端的减速比统一定义为：

```text
ratio_encoder_to_wheel = 编码器所在轴转数 / 轮端转数
counts_per_wheel_rev = counts_per_encoder_rev × ratio_encoder_to_wheel
```

如果已通过轮端转10圈得到 `counts_per_wheel_rev`，后续距离公式直接使用它，不再乘一次齿比。

## 4. 参数与板级绑定先于电机使能

### 4.1 硬件未绑定时必须明确阻止启动

`board_config.h` 中设置 `BOARD_PINMAP_CONFIRMED=0` 作为未适配状态。它为0时，构建可选择输出明确的编译错误，或生成只能显示诊断、不能启动电机的镜像；推荐正式应用构建直接拒绝。

不要用随意的A0、TIM1之类占位引脚拼出一个“能编译”的驱动车程序。实际表已完成，见[两份epro引脚与驱动核对](hardware/引脚与驱动核对.md)。最终表包含两路EN PWM、两路PH、两侧A/B、相机各线、控制节拍、UART及可选IMU的实际映射。

硬件检查需要核对：同一引脚不重复；PWM与编码器不抢同一定时器；PWM映射组一致；预留调试接口；驱动板和主控板有可靠信号地参考。

### 4.3 参数验证与默认值

任何可能进入除法或控制计算的浮点数先检查 `isfinite()`。轮径、轮距、有效计数必须大于零；η必须小于1；占空比在[0,1]；速度档不得超过两侧能力；软超时小于硬超时；ROI不得越图像边界。

未测的物理参数默认无效，不用65mm、140mm等算例数值代替实物。可提供静态图像预览默认值；正常发车则要求对应标定位有效。

预留 `TRACK_PROFILE_VALID`：实际Y数量、环岛入口/出口模板或判据尚未配置时，不能声称具备完整比赛任务能力。低速普通循迹可以作为明确的训练模式独立运行。

## 6. 时间基准和执行周期

第一版以5ms控制周期为起点，采用裸机调度；实际周期必须通过定时器或测量校验。

| 工作 | 执行位置 | 周期/触发 |
|---|---|---|
| 编码器采样、速度滤波、运行状态、目标限制、两个PI、PWM | 控制定时器ISR | 5ms起步 |
| DVP帧结束、冻结或确认缓冲状态、时间戳 | 已有DVP ISR的应用钩子 | 每个完整采集帧 |
| 图像扫描、路况状态、路径与转向 | 主循环 | 每个可取得的一致新帧 |
| 屏幕分块刷新、按键与低速诊断 | 主循环 | 有限预算，约5～10Hz |
| 参数写FLASH | 主循环，运行已禁止且控制器处于静止配置流程 | 人工保存动作 |

`board_time_ms()`是拟开发的板级时间接口。其来源应是已分配的单调计时器/可靠系统计数，不能占用模板延时或调试所依赖的计时资源。具体实现按资源表确定，不能假装逐飞已有这个同名函数。

所有超时使用无符号差值：`elapsed=(uint32_t)(now-start)`，要求超时间隔小于2^31ms。不要比较 `now > start+timeout`。时间戳分辨率必须足以支撑实际周期；PI的dt用测量或已验证周期转成秒。

中断不执行图像扫描、全屏刷新、FLASH擦写、阻塞串口输出、摄像头重新初始化或malloc/free。超出执行预算的操作必须留在主循环并限制单次工作量。

调度常量只在app_config.h定义一次，建议包括 `APP_CONTROL_PERIOD_MS`、图像尺寸/容量、日志容量和功能开关。控制周期改变后，要复核PI的dt、滤波时间常数、最大计数增量、超时和最坏执行时间，不把“5ms”复制到多个文件。

## 7. 运行模式与启动顺序

### 7.1 状态含义

| 模式 | 电机输出 | 可以做什么 |
|---|---|---|
| BOOT | 两路EN保持已确认的零输出/制动状态 | 初始化、验证参数与外设 |
| STATIC_DEBUG | 禁止电机运行 | 看图、菜单调参、手动编码器检查 |
| READY | 禁止电机运行 | 冻结下一次参数、准备会话和新帧 |
| RUNNING | 两套侧速度闭环 | 只按车载感知自动运行 |
| STOPPING | 按已确认的制动过程减至零 | 禁止新的路线推进和加速 |
| FAULT | 保持两路EN=0，锁存原因 | 查看诊断；本地确认后才允许重新准备 |

电机零输出在当前DRV8701E电路中通常对应低侧制动，不自动等于自由滑行或完全断电。紧急断电能力由实际硬件开关保证，不能编造一根不存在的MCU nSLEEP控制线。

### 7.2 初始化顺序

1. 在可操作GPIO后尽早让两路EN保持零，PH写入明确初值；硬件上电到GPIO配置之前的状态也要验证。
2. 保留模板 `clock_init()` 与 `debug_init()`，初始化单调时间与诊断。
3. 读取参数；验证格式、范围、板级资源与标定位。参数无效则留在静态诊断。
4. 初始化编码器，采样一次计数作为基线；初始化PWM为零，创建两个PI状态。
5. 准备好ISR会访问的状态，再初始化/使能控制节拍。即使ISR开始执行，模式仍禁止电机运行。
6. 初始化摄像头；这一步可能等待通信响应，但控制ISR继续维持零输出。失败不能进入READY。
7. 初始化可选IMU、显示和按键；验证图像与测速输入。
8. 进入STATIC_DEBUG或READY。发车需要本地明确动作和全部条件成立。

先写状态、后开中断，避免ISR访问未初始化结构。保留现有UART5摄像头配置回调和UART3 debug处理，不因接入应用而清空模板回调。

### 7.3 一次会话怎样开始与结束

运行模式和电机允许状态由控制ISR唯一持有。主循环只发布请求，不直接把共享模式变量写成RUNNING。

READY时，主循环准备 `next_session_id`，冻结待运行的参数，重置路线历史和路径控制状态，清空旧运动请求，再处理一张当前帧。准备结束后发布 `START(next_session_id)` 请求。

控制ISR接受START前必须再次检查：当前仍READY、session匹配、参数和编码器有效、运动请求新鲜且路径有效、没有停止/故障请求。随后把该session设为active，清两个PI积分及目标斜坡，并从零开始运行。

READY预览不能增加岔路通过次数，也不能把环岛状态推进到“已经完成”；只有active会话RUNNING时才提交路线事件。

停止/故障后：电机控制继续执行必要的制动流程；主循环停止提交路线通过事件。再次启动必须先回到READY并准备新session。故障恢复不自动复跑。

静态菜单配置与运行参数分开存放；READY冻结后，未结束会话不能原地改动参数。需要修改时先撤销准备并回到静态调试。

## 8. 中断和主循环怎样交换数据

采用单核、短临界区快照，第一版不写复杂锁或自旋循环。

| 数据 | 唯一写入者 | 读取者 |
|---|---|---|
| 两个PI、目标斜坡、SideFeedback累计状态、运行模式 | 控制ISR | 主循环通过ControlSnapshot读取 |
| 图像特征、TrackContext、Y历史、视觉PD状态 | 主循环 | 控制ISR只读最终MotionRequest |
| 帧READY/PROCESSING状态 | DVP ISR与主循环按所有权协议交接 | 两者各做规定的状态转换 |
| 待运行参数 | 静态主循环 | READY冻结后作为只读快照供两者使用 |
| START/STOP/故障清除请求 | 主循环通过请求接口发布 | 控制ISR消费并确认 |

`app_exchange_publish_motion()`：先在主循环局部变量里算完整结果，进入短临界区复制到共享结构，内存屏障后恢复原来的中断状态。不能无条件“开中断”，因为调用前可能本来已关中断。

`app_exchange_read_control()`：主循环用相同策略复制一个完整ControlSnapshot；不要在临界区内格式化打印。

请求邮箱保留STOP最高优先级，不能被随后到来的START覆盖。给请求加序号与确认号，主循环没有收到确认前不能认定启动或停止成功。状态快照先于同一轮图像决策读取，发布运动请求时携带该会话ID；ISR会拒绝会话不匹配的请求。

中断不会等待主循环完成发布。主循环复制大图像也不靠长时间全局关中断解决。

## 9. 两侧编码器模块：side_encoder.c

### 9.1 对外接口

拟开发接口：

```c
bool side_encoder_init(const VehicleParam *vehicle);
void side_encoder_reset_baseline(void); /* 仅停止/重置阶段 */
bool side_encoder_sample(float dt_s, uint32_t now_ms, SideFeedback *out);
```

init调用现有 `encoder_quad_init()`，参数来自已核对board_config。sample只在控制ISR调用；模块持有两侧上次raw、累计计数和滤波状态。

### 9.2 正确处理16位回绕

当前库在正交模式把CNT作为int16返回。先恢复位模式再差分。下例是纯计算参考：

```c
/* 使用 stdint.h。前提：硬件计数模数为65536，
 * 两次采样之间真实增量的绝对值严格小于32768。 */
static int32_t count_delta_u16(uint16_t now, uint16_t prev)
{
    uint16_t wrapped = (uint16_t)(now - prev);
    return wrapped < 0x8000u
        ? (int32_t)wrapped
        : (int32_t)wrapped - 65536;
}
```

对库返回值做 `(uint16_t)` 转换，再调用差分；之后乘各侧 `encoder_forward_sign`。不要在int16里先取负，因为-32768无法由int16表示其相反数。

启用该方案前核对计数器ARR和计数宽度。若ARR不是65535、计数位宽不同，改用实际模数；若最大轴速和采样间隔可能跨过半圈计数范围，缩短间隔或用正确的溢出扩展方案。漏掉多个控制周期后也要重新检查这个条件，不能悄悄按正常dt继续算。

### 9.3 计数换算与滤波

```text
delta_m[side] = π × side_diameter_m[side]
                × signed_delta_count / counts_per_wheel_rev[side]
raw_speed_mps = delta_m / dt_s
alpha = dt_s / (filter_tau_s + dt_s)
filtered_speed += alpha × (raw_speed_mps - filtered_speed)
```

dt和分母先验证。滤波时间常数是秒，不把某个固定α偷偷绑定到一个周期。累计计数用int64，累计距离用适当精度；所有读取都通过快照。

同侧前后轮的相对转动属于机械验收。单个电机轴编码器无法发现所有轮端松脱。诊断中应把“计数有效”和“真实地面运动正确”分开。

## 10. 两个速度PI：speed_control.c

### 10.1 状态和接口

```c
typedef struct {
    float integral_duty;
    float last_applied_duty;
    bool initialized;
} SpeedPiState;

void speed_pi_reset(SpeedPiState *state);
float speed_pi_step(SpeedPiState *state, const SpeedPiParam *param,
                    float target_mps, float measured_mps, float dt_s,
                    float duty_min, float duty_max);
```

应用创建 `SpeedPiState pi[2]`。每个状态只由控制ISR更新，不放在一个函数内的公共static变量里让两侧共用。

普通前进模式的PI输出边界为 **[0,duty_limit]**。速度超调时输出降至零，利用已验证的EN=0制动行为；不能让PI算出的负数直接变成反转PH。台架反转模式另行明确方向和输出边界。

### 10.2 更新步骤

```text
检查参数、目标、测速和dt是否有限且范围有效
error = target - measured
feedforward = target>0 ? ff_deadzone + ff_gain×target : 0
integral_candidate = clamp(I + Ki×error×dt, -I_limit, +I_limit)
raw_candidate = feedforward + Kp×error + integral_candidate

若输出已超上限且此次积分还向上推，拒绝此次积分增量
若输出已低于下限且此次积分还向下推，拒绝此次积分增量
其余情况接受integral_candidate

output = clamp(feedforward + Kp×error + I, duty_min, duty_max)
```

停止时重置积分的时机由run_manager决定：控制减速过程中可以继续以非负输出跟随下降目标；进入最终零输出/FAULT后强制清积分并保持零。禁止凭旧积分在停车后再次起动。

除PI自身限幅外，电机层还可能限制/拒绝输出。以实际应用输出更新诊断并在电机层拒绝驱动时复位或冻结积分，避免控制器以为已给出的指令实际没有执行。若以后增加占空比斜坡，须把执行器饱和反馈纳入抗积分饱和设计。

先Kp、再Ki、最后前馈校准；每次只改变一组参数。四轮落地转弯负载大于架空状态，架空调通后仍要重新验收。

增益单位也固定：速度Kp为“占空比/(m/s)”，Ki为“占空比/((m/s)·s)”，ff_gain为“占空比/(m/s)”。这里占空比用0～1表示，不直接使用0～10000的整数，否则同一个数字会差一万倍。视觉Kp把归一化误差变成rad/s，视觉Kd与按秒计算的误差导数配合使用。

## 11. PH/EN执行器：motor.c

拟开发接口：

```c
bool motor_init_zero(void);
void motor_apply_forward(float left_duty, float right_duty);
void motor_brake_zero(void);
bool motor_bench_request(SideId side, float signed_duty);
```

只有本模块与board_port可以操作EN/PH。`motor_apply_forward()`拒绝非有限值、负值和越界值；正常输出先限幅，再按 `round(duty×PWM_DUTY_MAX)` 转成uint32。两个EN共用频率时符合所选定时器规则。

PWM频率是板级参数。可以把20kHz作为待台架验证的起始候选，但它不是由图片或模板证明的最佳频率；需结合DRV8701、MOSFET开关损耗、温升与实测波形确认。

台架换向单独管理：请求变号→EN归零制动→等待连续若干速度样本低于阈值与已验证的最小等待时间→在EN=0时改变PH→按限制恢复输出。测速为零不代表绕组电流已完全为零，等待策略仍须台架验证。普通运行模式不调用此入口。

`motor_brake_zero()`不改变PH，只将两路EN降到0。需要真正断电或高阻状态时使用已核实的硬件能力，不通过代码假定当前nSLEEP已接入MCU。

当前板SP/SN接地、nFAULT/SNSOUT/SO未接回主控，因此不能提供 `motor_get_current()` 或“已确认驱动无故障”之类伪接口。可记录外部台架电流，固件只能报告自己实际拥有的测量。

## 12. 图像所有权：camera_frame.c

### 12.1 第一版采用受控暂停采集

当前库只有一块完整图像存储区。第一版选择“完整帧结束后暂停继续写入→主循环处理→释放后重新采集下一完整帧”，以获得一致数据，实际FPS随处理时间变化。

这是一项需要实现并验证的硬件适配，不是库当前已经提供的保证。需要按DVP实际帧边界停写、确认DMA停止修改、在正确同步边界重新接收完整帧。仅关闭NVIC、关帧中断或清finish_flag都不会阻止DMA覆盖。

如果该停止/重启方式在模块上无法可靠实现，应先完成双缓冲或受验证的ROI复制方案再放行。不能回退成“反正主循环读得很快”。

### 12.2 帧类型与接口

```c
typedef struct {
    const uint8_t *pixels;
    uint16_t width;
    uint16_t height;
    uint16_t stride;
    uint32_t frame_id;
    uint32_t capture_ms;
} FrameView;

bool camera_frame_init(void);
void camera_frame_on_done_isr(uint32_t now_ms);
bool camera_frame_acquire(FrameView *out);
void camera_frame_release(uint32_t frame_id);
```

pixels指向借用的缓冲，不表示调用者拥有可任意保留的副本。release之后所有读图必须结束，屏幕不能继续使用这个指针。

### 12.3 所有权状态

```text
CAPTURING：DVP拥有缓冲，主循环不得读作完整帧
   ↓ 完整帧完成 + 硬件已确认停止继续写入
READY：记录frame_id、capture_ms
   ↓ 主循环原子取得
PROCESSING：主循环拥有只读视图，DVP不覆盖
   ↓ 计算完特征及必要小缩略图后release
CAPTURING：重新接收下一张完整帧
```

异常状态单独记录：重启失败、帧尺寸异常、处理超时、重复释放、丢帧。运行中不阻塞控制ISR等待新图。

DVP IRQ保留一次原有 `camera_dvp_handler()`，再接应用钩子并按照已验证的硬件顺序完成暂停和通知。已有finish_flag可在适配层消化，主循环不得另写一套竞争的图像取帧逻辑。

### 12.4 内存和带宽

单帧22560B；两块同尺寸灰度帧为45120B，超过当前32KB RAM。主循环优先逐行处理，不额外建完整uint8二值图。

若保留每行最多4个白段，每段用left/right两个uint16，则120行边界存储约1920B，另加段数和候选轨迹。这个4是容量设计初值，行内白段超容量时标记歧义/溢出，不能悄悄截掉后仍输出高置信度。

32KB扣除灰度图和2048B栈后仅剩8160B，尚需全局变量、堆、调试缓冲和应用状态。最终以链接map为准，逐项列出实际sizeof和最大栈使用；库初始化malloc仍需要堆，不能当作零开销。

UART 115200按8N1发送一张22560B灰度图，线速下限约1.96s。全帧图传只作停车诊断，不能每帧阻塞发送。运行日志采用小报文低频发送，竞赛模式默认停用图传和外部控制入口。

## 13. 白线与候选路径：vision_line.c

拟开发接口：

```c
bool vision_line_process(const FrameView *frame,
                         const VisionParam *param,
                         uint32_t session_id,
                         /* 输出 */ VisionFeatures *features);
```

VisionFeatures在app_types.h中先声明/定义，再使用函数原型。以下给出固定容量结构示例，宏容量应统一写在app_config.h：

```c
#define APP_IMAGE_HEIGHT 120u
#define APP_RUNS_PER_ROW 4u
#define APP_PATH_CAPACITY 4u

typedef struct { uint16_t left, right; } WhiteRun;
typedef struct {
    WhiteRun runs[APP_RUNS_PER_ROW];
    uint8_t count;
    bool overflow;
} RowRuns;
typedef struct {
    float center_x[APP_IMAGE_HEIGHT];
    uint8_t row_valid[APP_IMAGE_HEIGHT];
    uint16_t valid_rows;
    float continuity_score;
    float width_score;
    float direction_trend;
} PathCandidate;
typedef struct {
    uint32_t frame_id, capture_ms, session_id;
    RowRuns rows[APP_IMAGE_HEIGHT];
    PathCandidate paths[APP_PATH_CAPACITY];
    uint8_t path_count;
    uint8_t cross_score, split_score, merge_score, island_score;
    uint8_t confidence;
    bool overflow, ambiguous;
} VisionFeatures;
```

center_x中无效行不得读取，必须先判断row_valid。候选路径编号是本帧数组下标，不能当作跨帧永远不变的身份。实际内存按编译器sizeof核算；这些数组放静态工作区，不塞进2KB中断栈或主循环的巨型局部变量。输出应包含：

```text
VisionFeatures
  frame_id、capture_ms、session_id
  每个ROI扫描行的白段数量、每段[left,right]
  当前候选轨迹（固定容量）
  各轨迹近中远中心、连续性、宽度合理性、方向趋势
  横线/分叉/合流/闭环结构的证据评分
  valid_rows、confidence、overflow、ambiguous
```

实现时在app_types.h中定义 `WhiteRun`、`RowRuns`、`PathCandidate`、`VisionFeatures` 四个类型，容量来自app_config.h。所有数组访问有边界；不根据图像内容动态malloc。

每行处理流程：

1. 检查FrameView尺寸与stride，ROI左闭右开。
2. 扫描像素是否高于阈值，找每段连续白色区。
3. 检查每行校准线宽；记录超宽区，但不要直接当普通主线。
4. 将相邻行段按中心距离、方向和宽度变化连接成候选轨迹。
5. 保留多个支路；由track_element选路，不能在这里求所有支路的平均中心。
6. 输出带时间戳的特征；无可靠轨迹时path_valid=false。

初版先固定阈值、固定ROI、少量多行跟踪，确保可解释。再加入平滑的自适应阈值和更完整的候选关联。十字横线可能是最长白段，因此“选最长段”不能是通用主线策略。

输出的confidence是可解释的评分：有效行比例、线宽合理性、连续性、分叉歧义等组成，范围0～100。写出每项如何加减分；不要把这个分数当作经过统计校准的概率。

图像空白、反光大面积白、段数超限、ROI内没有连续轨迹都必须成为明确的无效或低置信度结果，不能沿用旧数组中的中心点假装识别成功。

## 14. 路况选择：track_element.c

### 14.1 先定义输出，不让状态机直接操作电机

```c
typedef struct {
    TrackState state;
    uint8_t selected_path_index;    /* 只在当前features内有效 */
    uint32_t frame_id;
    uint32_t session_id;
    float speed_cap_mps;
    bool path_valid;
    bool reset_visual_derivative;
    bool stop_requested;
} TrackDecision;

void track_element_reset(uint32_t session_id);
bool track_element_step(const VisionFeatures *features,
                         const ControlSnapshot *control,
                         bool allow_event_commit,
                         TrackDecision *out);
```

内部TrackContext由主循环唯一持有，包含state、session_id、last_frame_id、进入时间、进入时累计路程、已选支路的预测轨迹、元素身份、Y历史和环岛证据。`allow_event_commit`只有当前会话RUNNING时为真，READY预览不增加通过次数。

同一frame_id只能推进一次状态。特征丢帧时用时间辅助判断，不能假定连续三帧永远等于60ms。候选数组下标改变时，通过上一帧轨迹位置和方向重新关联，不能因为下标换了就跳去另一支。

### 14.2 正常循迹和元素确认

NORMAL状态优先选择与近处有效胶带、上一帧预测和线宽相符的连续候选。超宽横线、分叉、闭环等证据达到确认条件才进入元素状态。单帧噪点不能提交元素。

多个类型证据同时成立时先标记歧义、降速和继续观察。Y和环岛都可能有分叉，不能用“看到两支”就立刻认定Y。现场元素拓扑尚未标定时，返回未解决状态，并在超时后请求停车。

### 14.3 十字状态表

| 状态 | 进入/维持动作 | 退出条件 |
|---|---|---|
| CROSS_CONFIRM | 保存进入前主线方向，确认横向宽白带与前方连续线 | 连续证据成立→CROSS_PASS；证据撤销→NORMAL |
| CROSS_PASS | 跟踪与进入方向最一致的前方路径，屏蔽横线诱导；限速 | 前方单线稳定且观察到出口区域→CROSS_CLEAR |
| CROSS_CLEAR | 保持直行路径锁定，继续低速通过 | 后轴通过辅助条件成立且视觉稳定→NORMAL |

任何阶段超过元素超时或所有候选都不可靠，进入DEGRADED并按运行规则降速/停车。不能转入左右分支以“找回线”，因为规则要求十字直行。

### 14.4 Y状态表与两圈路线历史

| 状态 | 动作 | 成功条件 |
|---|---|---|
| Y_CONFIRM | 确认空间分离的两支，确定该元素身份及本次A/B选择 | 路径可关联、身份可靠→Y_COMMITTED |
| Y_COMMITTED | 存下选中支路的几何描述，跨帧持续关联 | 两支逐渐合并→Y_MERGE |
| Y_MERGE | 继续跟随已选支路的自然延续，不重新按“最靠左”选路 | 合流后单线持续稳定→Y_CLEAR |
| Y_CLEAR | 维持低速，确认后轴也离开分支区域 | 成功后只提交一次通过事件，更新历史→NORMAL |

Y历史每个元素一条，固定容量，例如 `APP_Y_CAPACITY`，不能动态无限增长。每条至少含：valid、element_id、visit_count、passed_branch_mask、本次committed_branch、last_completion_frame。

第一次成功通过A后，第二次要求B；状态在MERGE前失败时不算通过。对相同元素一次行驶看见十帧，只提交一次完成事件。

只有确认每圈一个Y时才允许用全局访问次数交替。如果多个Y，使用经过验证的元素序列或身份关联，分别保存A/B历史；误认或超容量时降速并请求处理，不默默把所有岔路都归为同一个。

入口处A/B按进入方向下的一致几何顺序定义。局部图像通常无法判断哪条更长，不把A/B命名成“长路/短路”。

### 14.5 环岛状态与完成证据

| 状态 | 主要工作 | 到下一状态的依据 |
|---|---|---|
| ISLAND_CONFIRM | 区分环岛入口和普通Y，保存进入方向与本次环岛ID | 入口拓扑经现场模板/判据确认 |
| ISLAND_ENTER | 选择进环路径，限速并提交路径锁定 | 已进入可持续关联的环道 |
| ISLAND_FOLLOW | 跟踪环道，累计视觉事件、滚动里程和可选真实航向 | 证据组合确认完成一周，且发现可信出口 |
| ISLAND_EXIT | 选择出口，保持支路关联 | 出口单线稳定→ISLAND_CLEAR |
| ISLAND_CLEAR | 让后轴继续通过出口区域 | 辅助通过条件成立→NORMAL，并解除本次锁定 |

完成一周不是一个独立的“转够360°”条件。内部证据包含：进入后拓扑顺序、环道重复结构或再遇出口、最小环行过程、可选IMU有符号转角、事件间距。六个角点只作辅助，要防重复计角。

设置 `lap_evidence_valid` 与 `exit_path_valid` 两个独立标志：已绕完但没看清出口时继续低速跟环；看见出口但尚无完整绕行证据时不提前退出。达到异常时间/路程上限后请求停车，不能无限兜圈。

实际环岛入口、环道和出口图形尚需现场图片或采集帧。代码第一版应把相关模式配置为未标定，并通过 `TRACK_PROFILE_VALID` 阻止把占位检测器用于完整比赛模式。文档提供状态/数据/失败处理，不能替代缺失的现场几何资料。

## 15. 后轴是否通过：vehicle_progress.c

单纯“画面恢复一条线”不够。相机在高支架上看前方，后轴可能还没到该位置。

拟开发接口：

```c
typedef struct {
    bool metric_anchor_valid;
    float exit_boundary_x_at_anchor_m;
    float rolling_s_at_anchor_m;
    float anchor_heading_rad;
    bool heading_valid;
    uint32_t anchor_ms;
} ElementAnchor;

void vehicle_progress_reset(uint32_t session_id);
bool vehicle_progress_rear_clear(const ElementAnchor *anchor,
                                  const ControlSnapshot *control,
                                  bool exit_line_stable);
```

对接近直行的十字，若在记录anchor时已标定出口边界相对车身参考点的前方距离x_exit，后轴位置x_rear<0，则辅助距离门槛可写为：

```text
参考点前移距离 > x_exit - x_rear + clearance_margin
```

x_exit必须是需要离开的元素区域远侧边界，不是随便拿入口那条线。滚动里程仅作进度近似，并与出口单线稳定一起使用。

Y和环岛退出存在转弯，不能照搬直线路程条件作为精确后轴轨迹。初期用标定后的通过余量、持续视觉关联和录像验收；有地面路径/航向估计后，再检查四个接触点的短期预测轨迹。相机外参、轴距和滑移未标定时，rear_clear不能伪造“精确通过”，应保守维持状态或超时停车。

对十字/分叉的所有计算都相对本次选定路径。附近另一条白线不能让后轴通过条件误成立。

## 16. 路径到转向：path_control.c

拟开发接口：

```c
void path_control_reset(uint32_t session_id);
bool path_control_step(const VisionFeatures *features,
                        const TrackDecision *decision,
                        uint32_t now_ms,
                        PathObservation *observation,
                        MotionRequest *request);
```

一帧只更新一次视觉PD：

```text
从selected_path_index对应的有效行计算前瞻中心
e_right = (center_x - calibrated_center_x)/(image_width/2)
dt_visual = (capture_ms - prev_capture_ms)/1000
derivative_raw = (e_right - previous_e_right)/dt_visual
alpha_d = dt_visual/(derivative_tau_s + dt_visual)
derivative_filtered += alpha_d×(derivative_raw-derivative_filtered)
omega_raw = -(visual_kp×e_right + visual_kd×derivative_filtered)
```

有效行权重只对有效样本求和；权重和为零则无路径。dt为零、过小/过大、旧frame或错误session时拒绝导数更新。首帧、支路切换、重新识别和状态要求重置时，D从零起步。

这个omega_raw只是需求。模块输出TrackDecision允许的速度上限、capture_ms、session_id和有效性，由控制ISR的motion_plan统一限幅，不能在主循环直接输出左右PWM。

选用几何前瞻算法时，目标X/Y先变换到车身参考点的地面米制坐标，再计算κ=2Y/(X²+Y²)与ω=vκ。X²+Y²太小要拒绝；用像素坐标直接代入不成立。第一版仍以图像PD为主，几何模式通过配置互斥选择。

## 17. 路况速度与两侧分配：motion_plan.c

拟开发接口：

```c
void motion_plan_reset(void);
bool motion_plan_step(const MotionRequest *request,
                       const ControlSnapshot *previous,
                       const AppParam *param,
                       float dt_s, bool stopping,
                       SideTargets *targets);
```

### 17.1 处理顺序固定

1. 检查会话、时间戳、浮点、置信度和stop标志；不合格按run_manager策略降速或停车。
2. 按NORMAL、CORNER、CROSS、Y、ISLAND与置信度决定目标前进速度，不超过参数和请求上限。
3. 对目标前进速度做加减速限制，得到本周期v。
4. 普通前进模式限制转向：`|ω|≤2(1-η)v/b`。b使用有效且经过范围检查的b_eff，否则使用b_g。
5. 当v接近零时ω明确归零；转换为侧目标 `vL=v-ωb/2`、`vR=v+ωb/2`。
6. 若任一侧超上限，按同一比例缩小两侧目标。先检查零分母；左右上限不同则分别算比例后取最小。
7. 用成对变化率限制让两侧目标从上一周期平滑走向新目标，再最终检查非负和能力边界。

在固定κ下，降低v不会改变左右速度比，也不会改变内侧是否被要求反转。若持续触发曲率限幅，应调整目标路径/前瞻和入弯策略；不能宣称限幅后仍严格沿原曲率行驶。

### 17.2 成对变化率限制

```text
dL = wantedL - previousL
dR = wantedR - previousR
根据每侧本次是加速还是减速，选相应允许变化量limitL、limitR
lambda = min(1, limitL/abs(dL), limitR/abs(dR))  // 差值为零的项不参与除法
nextL = previousL + lambda×dL
nextR = previousR + lambda×dR
```

两个端点都非负且不超过各侧上限时，这个凸组合仍在边界内。它限制传动突变，但过渡期间曲率可能变化，所以记录实际分配后的模型v/ω，而不是继续输出“原始目标已完全实现”。

### 17.3 丢图与停车

软超时或短时低置信度：停止加速，按最近可靠的受限曲率减速，保持时间有上限。不能固定旧ω而把v单独降到零。

硬超时、非有限计算、严重控制异常：锁存故障并按已验证策略使EN归零；不经过会再次加速的普通路径。普通本地停止走STOPPING斜坡，最终零输出后清PI。停车的目标归零与车实际完全停止分开记录，不能因目标为零就声称车已静止。

## 18. 固定周期入口：app_control.c 与 zf_isr.c

拟开发接口：

```c
bool app_control_init(const AppParam *frozen_param);
void app_control_tick_isr(uint32_t now_ms);
bool app_boot_init(void);
void app_main_poll(void);
```

app_control持有两个PI、侧目标斜坡、编码器采样状态和运行监督状态。ISR每次执行：

```text
记录进入时间，计算并校验dt
采样两侧编码器，得到SideFeedback
取一个完整MotionRequest快照和待处理请求
处理运行状态转换、会话匹配、故障优先级

若BOOT/STATIC_DEBUG/READY/FAULT：
  保持EN=0，按状态规则清积分和目标
否则若RUNNING/STOPPING：
  检查视觉结果年龄和输入有效性
  motion_plan得到两侧目标
  两套PI各自计算，普通模式输出非负
  motor_apply_forward；异常则motor_brake_zero

发布ControlSnapshot
记录执行时间和超周期计数
```

接入已有定时器IRQ，例如**只有资源表确实分配TIM6时**，在现有 `TIM6_IRQHandler()` 的更新标志处理内清标志并调用app_control钩子；不要在新文件再定义一个TIM6_IRQHandler。初始化使用库真实的 `pit_ms_init()` 与对应枚举，不能照抄其他芯片的 `PIT_TIMG0`。

DVP默认优先级与控制PIT默认优先级不同，加入暂停/通知后测量控制周期抖动。确认相机ISR短、临界区短，不能为了相机整帧处理占用高优先级中断。

时间预算示例：5ms控制周期，目标让最坏ISR计算明显小于周期并留出其他IRQ余量；文档不宣称一个未经测量的微秒数。检测到持续超周期就锁存诊断，不能靠主循环补跑多次PI伪装正常节拍。

显示缩略图可以在释放前复制少量像素到专用小缓存，释放后慢慢刷屏。不要因绘制整张图把采集一直停住，更不能释放后继续读原图指针。

## 20. 故障、超时与比赛通信模式

| 触发 | 处理 | 恢复条件 |
|---|---|---|
| 视觉短时置信度下降 | RUNNING降速，有限保持上次可靠路径 | 新帧恢复后缓慢恢复速度 |
| 图像持续过期/无路径 | STOPPING或FAULT，按严重程度和策略归零 | 停车、本地确认、准备新会话 |
| 计数跳变量超过物理可行范围 | 拒绝该测速结果，停止/故障 | 检查接线、采样遗漏、模数 |
| 目标、参数或计算出现NaN/Inf | 立即禁止正常驱动，记录STOP_NONFINITE | 排除原因后重新准备 |
| 元素身份不明或处理超时 | 受控降速/停车，记录现场帧ID | 不能自动宣布元素已成功通过 |
| 控制ISR持续超预算 | 故障归零、保留最小诊断 | 减少阻塞和中断占用 |
| START携带旧session | 拒绝，不改变输出 | 准备匹配的新会话 |

不能把“编码器没计数”单独当作精准堵转检测。可以结合目标较高、PWM较大、持续无转动作异常启发式，但它没有测量绕组电流；不能替代硬件过流保护。

默认启动功能检查和软件看门条件通过后再考虑硬件看门狗。喂狗条件应包含控制周期与主循环/视觉确实有进展，不能只在一个仍然正常触发的中断里无条件喂狗。

竞赛模式禁止外部通讯更改运行状态。USART RX可以保留协议解析，但所有会写配置、启停或路线的命令在active会话被明确拒绝。无线图传/遥测默认关闭，避免产生规则争议；本地物理安全处理按现场许可和比赛规则执行。

## 21. 参数保存与诊断：param_store.c、debug_view.c

### 21.1 FLASH格式

参数保存包含magic、schema_version、payload_len、sequence、显式编码payload、CRC、提交标记。不要直接把含bool、padding和编译器布局的整个C结构当作长期磁盘格式。

若使用两个存储槽：选择旧槽以外位置擦写→写头与payload→读回校验→最后写提交标记。掉电后只选择提交完整且CRC正确、版本可识别的最高有效序号。擦写单位、保留地址和固件链接边界按芯片与实际分区核对；不在文档里随意指定某个FLASH尾地址。

只在已停止且不再依赖实时采集/控制输出的维护流程保存：先禁止驱动，暂停相关采集和控制中断，完成擦写后重建计数基线、时间和图像状态，再回静态调试。新参数必须重新验证，不能保存后直接恢复旧RUNNING。

参数未初始化时，静态菜单显示“轮径未标定”“计数未标定”等具体原因，正常发车拒绝。不要默认给一份虚构物理尺寸让车自动启动。

### 21.2 屏幕与日志显示什么

| 页面 | 核心内容 |
|---|---|
| 运行状态 | 模式、会话ID、停止原因、参数版本 |
| 侧驱动 | 两侧目标/实测速度、PWM、原始计数增量 |
| 视觉 | 帧ID、帧年龄、有效行、置信度、选中路径 |
| 路况 | 状态、元素身份、Y分支历史、环岛证据 |
| 结构标定 | 四轮直径、轮距轴距、计数比例、编码器所在轴 |
| 时序 | 控制周期、最坏执行时间、处理帧耗时、丢帧/超时次数 |

每条日志带版本或包类型与时间戳，优先固定长度或有限长度报文。TX环形缓冲满了就计数并丢低优先级日志，不能等待。115200串口下例如64字节×10Hz约640B/s，远小于整帧图传；具体占用仍按实际数据核算。

当前板没有电流ADC/nFAULT反馈时，界面对应项显示“未接入”，不能显示一个固定0A或“驱动正常”误导调试。

## 22. 从零到整车的编码任务单

以下每阶段只写本阶段需要的文件，编译通过并确认观察结果后再接下一层。时间由实物调试决定，不给未经测量的固定完工承诺。

| 阶段 | 写入/接入的文件 | 必须看见的结果 | 暂不放行什么 |

| C9 十字 | track_element CROSS、vehicle_progress | 直行并保持锁定至后轴通过 | 不误选横向白段 |
| C10 Y | Y识别、路径关联、历史 | 一次元素只记一次，两次访问选不同支路 | 多Y未辨认身份时不全局乱切 |
| C11 环岛 | 环岛判据和FSM | 进环、完成一周、选出口、后轴离环 | 无现场判据不返回假成功 |
| C12 两圈与比赛模式 | run_manager、param_store、诊断限制 | 重发车状态清空、无外部干预、有效完整任务 | 不用运行秒数冒充圈数 |

每阶段完成后保存一个可恢复的提交，提交说明写明：新增能力、构建结果、台架/场地条件、实测值和已知限制。不要把“能编译”写成“整车通过”。

## 24. 完整任务验收与仍需填写的硬件项

代码完成不以文件数量判断。至少应满足：

- 两路电机各驱动同侧前后轮，传动和编码器换算正确。
- 两侧速度PI在实车负载下工作，普通循迹无意外反转。
- 帧所有权、控制周期、超时和停止路径可解释且有测量。
- 十字直行、Y两圈走不同支路、环岛完整一周，状态解除考虑后轴。
- 能连续完成两圈，重新发车不携带旧状态，发车后不依赖外部通信。
- 参数版本与当前代码匹配，已保留能恢复的稳定版本和实测记录。

仍需实物/现场资料填写的内容：电机型号、四轮有效直径、轮距轴距、总齿比、编码器安装轴与信号模式、精确引脚和timer分配、摄像头模块版本、实际RAM分区、可选IMU、环岛拓扑、Y元素数量与身份、终点可识别标记。

这些缺项不妨碍按接口顺序开发和主机验证；它们会阻止相应硬件功能或完整比赛模式放行。不得用猜测值去消除文档里的“待测”。

## 27. 各模块实现时的接口清单

表中名称属于拟开发应用接口；需要新增的辅助类型在app_types.h或模块私有头文件定义。对外尽量传入具体类型，禁止用void*掩盖尚未决定的数据结构。

| 模块 | 必须实现的入口/约定 | 调用位置与所有权 |
|---|---|---|
| board_port | 时间戳、保存/恢复中断状态、PWM/GPIO适配、DVP帧边界停写/重启 | 封装真实硬件；临界区不得等待；具体寄存器实现须核对 |
| app_boot | `app_boot_init()`，验证配置并保留初始化失败原因 | main初始化；失败保持电机禁止 |
| app_control | `app_control_init()`、`app_control_tick_isr()` | 持有侧采样、目标斜坡、两个PI与运行监督状态 |
| app_exchange | `app_exchange_publish_motion()`、`app_exchange_read_control()`、请求发布和确认 | 快照复制；停止请求不被启动覆盖；主循环发布/读取 |
| run_manager | 按第7节定义准备、启动、停止、故障和本地清除请求的处理函数 | 模式由控制ISR更新；主循环不直接写RUNNING |
| side_encoder | init、reset_baseline、sample | sample仅控制ISR调用 |
| speed_control | reset、step | 左右侧两个独立实例 |
| motor | init_zero、apply_forward、brake_zero、受限bench_request | 正常输出由控制ISR唯一执行；台架请求也经监督层执行 |
| camera_frame | init、on_done_isr、acquire、release | ISR生产完整帧；主循环借用并及时释放 |
| vision_line | process | 主循环，静态工作区，返回多候选与明确无效结果 |
| track_element | reset、step | 主循环，保存本会话路线历史 |
| vehicle_progress | reset、rear_clear | 主循环，使用一致控制快照；不冒充精准定位 |
| path_control | reset、step | 主循环，每张新帧最多一次PD更新 |
| motion_plan | reset、step | 控制ISR；限制和成对变化率处理后才给PI |
| param_store | load、validate、save、读取错误原因 | load/validate在初始化或静态模式；save按静止维护流程 |
| debug_view | 初始化、有限预算poll、快照展示和本地请求发布 | 主循环；没有直接写PWM或覆盖运行参数的权限 |

运行参数的生命周期：静态编辑区→validate→READY准备时复制/冻结→START确认后只读→结束会话后才允许替换。app_control初始化时先持有无输出的状态；切换到新的冻结参数必须经过READY准备协议，不能让它一直引用一个会被菜单原地改动的AppParam。

最小依赖建议：app_types只依赖stdint/stdbool及容量宏；纯算法模块依赖app_types和参数；board_port负责引入逐飞硬件头文件。每个.c只定义自己的模块状态，.h中用extern声明必要对象而不定义全局实例。禁止在头文件中定义两个PI或图像工作区造成多重定义。

正式接入后编译检查GNU11、硬浮点ABI与预编译库兼容；不要为解决单个编译错误随意修改模板的架构/ABI。新增文件是否纳入构建、原有IRQ是否重复、链接RAM/FLASH是否超限，要在每阶段构建日志和map里确认。
