# V1.50.11为何无法显示相机：与已验证HEX的详细对比

## 结论和证据范围

已证实的错误是软件I²C延时空循环被优化删除：用户确认可用的E02_uart_demo.hex使用-O0，V1.50.11使用-Os。两份ELF记录的编译器都为xPack GCC 8.2.0，不是更换了编译器版本。原驱动的延时写成非volatile空循环，在-Os下完全消失。

这是具体的软件缺陷，足以破坏相机SCCB配置通信，并与先前实测ID读回0xFFFF、初始化E1相符。V1.50.12已修复该机制并通过机器码回归；由于本次WCH-Link打开失败100，尚未完成硬件因果闭环，不声称画面已经恢复，也不排除恢复初始化后还有独立的采集问题。

## 比较对象

1. 用户明确确认可用的`Project/Project/mrs/obj/E02_uart_demo.hex`及同目录ELF、makefile、.compile_c_flags。HEX SHA256为`16ff310b9dde0a3082ecc6411e423f3050ed587697af1b831886f6a5ba66bad5`。
2. 发布的V1.50.11 HEX/ELF。
3. 只修复软件I²C延时机制的V1.50.12，继续-Os优化。

Desktop/Project中的main、ISR、相机.c/.h、软件I²C驱动、GPIO驱动及配置库与之前收到的Project.7z内容相同。之前重编Project.7z时也使用了-Os，因此重编版失败不能用于排除软件问题，更不能据此断定相机硬件损坏。那次测试烧的是重编产物，并非用户指定的已验证HEX。

## 发生了什么

原延时定义：

```c
#define soft_iic_delay(x) for(uint32 i = x; i--; )
```

循环里没有寄存器读写、volatile访问或其他可观察操作。GCC优化时可以把它删除。-O0下碰巧保留，所以原始HEX可用；-Os下仅剩连续翻转GPIO，没有原本请求的等待。

反汇编结果：

- 可用ELF：START中有两次从结构体offset12读取delay、计数递减及向后分支，例如0x816→0x80a、0x860→0x854。
- V1.50.11：soft_iic_start位于0xa546，只有GPIO操作，没有延时循环，也没有读取delay字段。
- V1.50.12：soft_iic_start两次调用soft_iic_delay；该函数包含volatile栈计数读写、nop及向后跳转，-Os无法再把等待删掉。

对应四份反汇编文本及文件哈希位于`release/v1.50.12`。GCC关于volatile访问的说明见[官方文档](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html)。这里用volatile保证等待不会消失，不把它当作通用的线程同步方案。

实际链路顺序是：软件I²C/SCCB识别相机→配置传感器→初始化DVP→收到完整帧→显示。此前在识别阶段就读到0xFFFF，根本尚未获得可显示的帧。因此先替换屏幕绘图函数或调整PCLK并不能修复这一通信缺陷。

## 修复与回归

仅将延时改为volatile计数循环，循环中加入nop及编译器memory屏障。主项目仍使用-Os，不把全部视觉和控制代码改成-O0。此循环不是按微秒标定的API；绝对SCL频率和电气时序仍需上板或示波器测量。

没有修改motion_plan、速度PI、元素状态机或原超时阈值。标定门槛不变，修复相机不等于允许未标定整车运动。

新增`tools/test_soft_iic_timing.py`直接检查实际目标ELF。它同时识别内联延时循环和调用公共循环函数两种形式：对已验证ELF通过，对V1.50.11报`0 waits`，对V1.50.12通过。该检查已加入tools/build.py，之后构建若再次删除总线等待会失败。它检查“是否保留等待”，不能代替波形测量。

验证结果：八组主机回归通过；WCH目标构建通过，Flash83684B、RAM31624B；目标ELF保留两次有效START等待。烧录尝试返回100，未写入，因此初始化返回0、帧编号持续增长、移动镜头画面随动、stop/back及再次进入的实物验证尚未完成。

手动烧录文件：`release/v1.50.12/second-test-v1.50.12.hex`。成功标准是初始化返回0且image和start页出现持续更新的画面；单看“编程成功”或“Cam OK”字样不足以验收。
